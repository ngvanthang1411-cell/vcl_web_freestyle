# You Got Bars?

A browser freestyle rap challenge. Pick a beat, hit the prompt words, record your
bars, and get scored on the Hype Meter.

Everything runs client-side. No backend, no API keys, no accounts — the app is a
static bundle you can host anywhere.

---

## Prerequisites

- **Node.js 18 or newer** (developed against Node 24)
- **npm 9+** (ships with Node 18+)
- A modern browser: Chrome, Edge, Firefox, or Safari 14.1+

## Install and run

```bash
npm install       # install dependencies
npm run dev       # start the dev server
```

Then open **http://localhost:5173**.

### Production build

```bash
npm run build     # outputs to dist/
npm run preview   # serves dist/ locally on http://localhost:4173
```

The `dist/` folder is plain static output — drop it on Netlify, Vercel, GitHub
Pages, S3, or any web server.

## Languages

The interface ships in **English** and **Vietnamese**. Switch languages with the
toggle in the top-right of the app bar, available on every screen.

- The choice is saved to `localStorage` and restored on your next visit.
- On a first visit the app picks Vietnamese automatically if your browser's
  language is `vi`, otherwise English.
- The word challenge uses a **separate word bank per language** — the prompt
  words are Vietnamese when the interface is, so you freestyle in the language
  you chose.
- Beat titles are track names and stay the same in both languages; their mood
  descriptions are translated.

### Adding a language

1. Add the locale to `LANGUAGES` in `src/i18n/translations.js`.
2. Add a locale block with the same keys as `en`.
3. Add a word bank for it in `src/data/words.js`.
4. Add a mood for each beat in `src/data/beats.js`.

Then run `npm run check:i18n` — it fails if any key is missing, orphaned, or
uses different `{placeholders}` between locales.

## Browser permissions

This app records your microphone, and optionally your camera. Browsers only grant
that access in a **secure context**:

| Where you serve it | Microphone / camera |
| --- | --- |
| `http://localhost:5173` | ✅ Allowed — `localhost` counts as secure |
| `https://your-site.com` | ✅ Allowed |
| `http://192.168.1.16:5173` | ❌ Blocked — a LAN IP over plain HTTP is not secure |

If you want to test on a phone or another machine on your network, use HTTPS —
`npm run dev -- --host` plus a tunnel such as `ngrok http 5173` or
`cloudflared tunnel --url http://localhost:5173` will do it.

**If you deny the permission**, the app does not dead-end. It explains how to
re-enable it and lets you continue in **practice mode**, where the word challenge
and scoring still work but nothing is recorded.

To re-enable access in Chrome: click the icon in the address bar → *Site
settings* → set *Microphone* to *Allow*, then reload. In Safari: *Settings →
Privacy & Security → Microphone*, or the *padlock* icon in the address bar.

### Autoplay policy

Browsers block audio that starts without a user gesture. Every audio action in
this app is triggered by a click or key press — the beat preview, the session
start — so audio never starts silently.

## Swapping in your own beats

The bundled beats are **synthesized drum loops** generated by
`scripts/generate-beats.mjs`. They contain no sampled or copyrighted material,
so they are free to redistribute.

To use your own:

1. **Drop the audio into `public/beats/`.**
   ```bash
   cp ~/my-tracks/hard-street.mp3 public/beats/hard-street.mp3
   ```
   Files in `public/` are served from the site root, so `public/beats/foo.mp3`
   is reachable at `/beats/foo.mp3`.

2. **Add an entry to `src/data/beats.js`:**
   ```js
   {
     id: 'hard-street',
     title: 'Hard Street',
     src: '/beats/hard-street.mp3',
     bpm: 96,
     duration: 24,        // seconds — shown on the card
     mood: 'Hard, street-level bounce',
   }
   ```

3. **Rebuild** (`npm run dev` picks it up automatically).

**Format notes:** WAV or MP3 both work. Keep files reasonably small — the app
streams them to the browser, so a 5 MB MP3 is fine but a 60 MB WAV is not.
`duration` is used for the preview progress bar and the card readout; it is not
read from the file, so keep it accurate.

If you remove the placeholder beats, you can also delete
`scripts/generate-beats.mjs` and the `generate:beats` script from
`package.json`.

## How the Hype Meter is scored

The score is deterministic and uses only measured values — no fake telemetry:

| Input | Contribution |
| --- | --- |
| Time freestyled ÷ session length | up to 40 points |
| Words hit ÷ words shown | up to 30 points |
| Hits that landed on the beat | up to 18 points |
| Session ran to completion | +8 points |
| A recording was captured | +4 points |

The weights add up to exactly 100, so a flawless run scores 100 and the clamp
never actually has to bite. The score is mapped onto tiers: *Warming Up* →
*Getting Warm* → *Hype* → *On Fire* → *Legend*. Practice mode (no recording)
is capped at 81, just below the top tier.

### Timing against the beat

Words are revealed on the beat, and the beat clock is the audio element's own
clock — sampled every animation frame, not on the `timeupdate` event, which
only fires about four times a second.

A hit is judged against the nearest beat:

| Offset from the beat | Judgement | Feedback |
| --- | --- | --- |
| within 90 ms | perfect | the word explodes — a ring and eight rays |
| within 160 ms | good | a smaller, dimmer burst |
| beyond that | off-beat | the word only glows faintly |

Only perfect hits count towards the timing points. The on-beat count travels
in the share link under the `p` key; links made before this feature existed
have no `p` key and are read as zero.

The beat files are trimmed to their musical grid (8 bars, 16th-note steps) by
`npm run trim:beats`. Without it each file carried 0.5s of trailing silence,
which became an audible gap on every loop repeat.

## Accessibility

- Semantic landmarks (`main`, `header`, `footer`) and real `<button>` elements
- ARIA labels on icon-only and slider controls; `role="timer"` and
  `aria-live` where state changes should be announced
- Keyboard-navigable throughout — the word challenge responds to the space bar,
  and every control is reachable by tab
- Visible focus rings (2px accent outline, 2px offset) on every interactive element
- Text meets WCAG AA contrast against the dark surface — the palette is checked
  against the four surface levels in `scripts/derive-palette.mjs`
- `prefers-reduced-motion` collapses the word entrance, the hit press and the
  hit ring

## Design system

The palette is a **sunset sweep** built from the VCL wordmark's own orange.

The logo carries exactly two colours: an orange ink and a black keyline. The
orange is the anchor, and the other two accents are derived from it by
walking the hue wheel toward sunset — orange (32°) → pink (333°) → violet
(274°). The three sit roughly 59° apart, so they read as one continuous warm
ramp rather than three unrelated colours, and the interface stays in the same
family as the wordmark.

Surfaces are a warm near-black with a violet cast, so they sit *under* the
accents rather than fighting them. Dark mode is the default.

**The accents are measured, not eyeballed.** The dominant ink in
`public/logo.png` is `#F78501` (H32 S99% L49%), and every ramp step holds its
family's hue while moving only lightness. Two values were moved for contrast
rather than looks, and the derivation script is what caught both:

- `--color-tertiary` is `#BE70FA`, not the more usual `#A855F7`. At its natural
  lightness the darker violet only reached 3.86:1 on the lightest surface —
  below the WCAG AA threshold of 4.5:1 for text.
- `--color-content-subtle` is `#948DA6`, lifted from `#8B849E` for the same
  reason.

The interface itself stays on the primary accent. The secondary and tertiary
families are there for a second level of emphasis when a screen needs it —
they are not used decoratively.

### Regenerating the palette

```bash

npm run crop:logo   # crop logo.png to its alpha bounds
```

`src/theme.css`, plus the contrast ratio of every accent step against the four
surface levels. If the logo changes, run it and update the theme file to match.

The derivation lives in `scripts/derive-palette.mjs`, with the colour maths in
`scripts/lib/palette-core.mjs`.

### Keeping it minimal

Outside the freestyle stage, the interface is deliberately plain: a header
with the brand and the language switcher, a title with one line of supporting
text, one primary action, the content, and a one-line footer. There is no side
navigation — each screen moves the flow forward with its own action, so the
chrome does not repeat it.

Decoration lives in the type, the spacing and the hairline borders, not in
animation or glow. The animations that remain are the word rising into place,
the word's press on a hit, and the ring that marks a hit — each one carrying
information rather than atmosphere.

### The freestyle stage

The challenge screen is a modern dark stage, in `src/stage.css`. It is the one
place in the app that is atmospheric, because it is the one place the player is
reading under time pressure.

From top to bottom:

- **The equalizer ring** — a circle of ticks drawn on a `<canvas>`, with the
  player's name and the tempo in the middle and the hit counter below. Each
  tick breathes on the beat, and a slow wave travels around the ring, so it
  never blinks as one block.
- **The target frame** — a recessed glass well with four thin corner brackets.
  It clips its overflow, so a card leaving the top is cut off cleanly instead
  of spilling over the page.
- **The card carousel** — the active word in the frame, with the upcoming
  words queued below it. Each card behind is smaller, dimmer and cooler than
  the one in front.
- **The session rail** — a thin gradient rule at the foot of the stage.

#### Everything moves with the beat

The tempo is never hardcoded. It comes from the beat that is loaded, and the
beat position is sampled from `audio.currentTime` — the same clock the hit
judging uses, so what you see and what you are scored on can never disagree.

Two hooks carry that:

- `useBeatTimeline` samples the audio clock every frame and reports the phase
  within the current beat. The canvas draws from it directly, so the ring
  costs no React re-renders.
- `useBeatClock` reports beat boundaries. The word reveal and the carousel
  both hang off it.

The carousel's GSAP tween is measured in **beats**, not milliseconds — a card
takes one beat to travel up its slot, which is exactly the time until the next
word is due. Change the beat and the motion retimes itself:

| Beat | Tempo | Card travel |
| --- | --- | --- |
| After Hours | 78 BPM | 0.71s |
| Rooftop Radio | 98 BPM | 0.56s |
| Chrome Crest | 126 BPM | 0.44s |

GSAP is imported by file path (`gsap/gsap-core.js` plus `gsap/CSSPlugin.js`)
rather than through the package entry, so the plugins this screen does not use
— ScrollTrigger, Observer, Flip — stay out of the bundle.

#### The card carousel

`WordCarousel` keeps the words as a deck of elements that move between slots,
rather than remounting them. On each new word:

1. the card at the head of the queue slides up into the frame and scales up;
2. the card that was in the frame keeps going up, shrinking and fading as it
   passes the top edge;
3. the cards behind it each slide up one slot, and the new card enters from
   below.

Every word carries a stable id, so the carousel animates the *same* element as
it moves up — the transition is a physical movement, not a crossfade. The
timelines are tracked and killed on unmount.

The queue is materialised from the same word source that feeds the prompt, so
a word you can see coming is exactly the word that will appear — the preview
can never drift out of sync with the reveal.

## Known limitations

- **Safari records MP4, not WebM.** Safari's MediaRecorder produces
  `video/mp4` / `audio/mp4`. The export button names the extension from the
  actual blob type, so Safari downloads `.mp4` and other browsers download
  `.webm`. Converting MP4 to WebM in-browser would need a muxing library, which
  is out of scope here.
- **No MP4 export from Chrome/Firefox.** Producing MP4 would require encoding
  the WebM stream in JavaScript. WebM is the native output, so that is what you
  get.
- **The beat is not mixed into the recording.** The beat plays from your
  speakers while MediaRecorder captures the microphone, so your take contains
  your voice (and whatever the room picks up) but not the instrumental. Mixing
  the two would require routing the beat through a `MediaStreamDestination` and
  combining the tracks — doable, but it is a larger change than this scaffold.
- **The share link carries the score, not the audio.** It encodes score, time
  and word hits into the URL fragment (`#result=…`). There is no upload step,
  so the recording never leaves the machine.
- **One shared `<audio>` element.** This is deliberate — it prevents the
  "play() request was interrupted by a new load request" errors you get from
  swapping `src` on multiple elements. The trade-off is that the beat cannot
  play at the same time as the results playback.
- **`createMediaElementSource` is called once per page load.** The browser
  forbids calling it twice on the same element, so the beat analyser is wired
  up on first play and reused for the rest of the session.
- **The video preview is not mirrored.** The camera preview shows the raw
  feed. A `scale-x-[-1]` transform would be a one-line change if you want the
  familiar selfie view.
- **Safari on iOS requires a user gesture for the first `getUserMedia` call.**
  The app already asks for permission from a click handler, so this works — but
  iOS Safari may reclaim the microphone when the tab is backgrounded mid-session.
